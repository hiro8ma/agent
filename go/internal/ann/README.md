# ann

近似最近傍探索（ANN）の主な方式を L2 距離で実装し、全探索と比べて recall@20 / 速さ / メモリ / 構築時間を測る

教材は Python / NumPy の例で、全探索を「ノルムの展開 + 内積 + 並べ替えない選択」で書き、ANN として PQ / IVF / LSH / HNSW を紹介している
ここでは同じ実験を Go で書き直し、各方式を自前で実装して Apple M5 Pro で測った

## 構成

| ファイル | 中身 |
| --- | --- |
| `exact.go` | `Exact`。`||q-x||² = ||q||² + ||x||² - 2q·x` の `||x||²` を先に持つ全探索。ヒープ（`Search`）/ quickselect（`Partition`、argpartition 相当）/ 4 本ずつ内積を取るバッチ（`SearchBatch` / `SearchBatchParallel`）/ 候補の並べ直し（`Refine`） |
| `pq.go` | `PQ` / `PQIndex`。直積量子化と ADC（クエリごとに M×K の距離表を作り、符号で表を引いて足す）、候補を元のベクトルで並べ直す `SearchRefine` |
| `ivf.go` | `IVFFlat` / `IVFPQ`。k-means の中心でクラスタに分け、近い nprobe 個だけを探す。IVF-PQ は所属クラスタの中心を引いた残差を、全クラスタで共有する 1 つの PQ で符号にする |
| `lsh.go` | `LSH`（ランダム超平面の SimHash、XOR と `bits.OnesCount64` のハミング距離で全走査して上位 C 件を並べ直す）と `LSHIndex`（SimHash の b ビットをバケット番号にした転置ファイル、ハミング距離 1 の隣を探すマルチプローブ） |
| `hnsw.go` | `HNSW`。層の高さの抽選、上の層の貪欲な降下、efConstruction の候補から辺を選ぶヒューリスティック、efSearch の探索。`Flat` で 1 層の NSW、`Greedy` で候補 1 つの貪欲探索 |
| `knngraph.go` | `NewKNNGraph`。正確な k 近傍だけを結ぶ 1 層のグラフ（長い辺が無い比較用） |

乱数はすべて種で固定し、同じ入力と設定なら同じ索引を作る

## 動かし方

```bash
go test ./internal/ann                       # 単体テスト（数秒）
go test -run '^$' -bench . ./internal/ann     # 距離表あり / なしの PQ
ANN_EVAL=1 go test -run 'TestReport' -v -timeout 0 ./internal/ann                       # 10 万件の表
ANN_EVAL=1 ANN_EVAL_N=100000,1000000 go test -run 'TestReportMethods' -v -timeout 0 ./internal/ann
```

SIMD の内積との比較は、`GOEXPERIMENT=simd` でビルドする別モジュールの `simdsearch` に置いた（`cd simdsearch && make knn`）

## 測定結果

Apple M5 Pro、Go 1.27、1 goroutine（全コアと書いたもの以外）
同じマシンで仮想マシンが CPU を 3〜4 コア分使っていたので、時間は 2 割ほど揺れる

### 全探索（N=100 万、d=128、K=20、正規乱数）

| 実装 | 1 クエリ |
| --- | --- |
| NumPy 2.5（OpenBLAS、教材のコードを同じマシンで実行） | 33 ms |
| 教材の値（Intel Core i7-12700K） | 34 ms |
| Go スカラ、ヒープ | 37〜52 ms |
| Go スカラ、quickselect（argpartition 相当） | 40〜77 ms |
| Go スカラ、32 本を 4 本ずつ内積（1 goroutine） | 30 ms |
| Go スカラ、32 本を 4 本ずつ内積（全コア） | 2.0〜5.8 ms |
| Go Neon `DotSIMD8A`、ヒープ（simdsearch） | 17〜19 ms |
| Go Neon `DotSIMD8A`、1 本を全コア（simdsearch） | 6.5 ms |
| Go Neon `DotSIMD8A`、32 本を全コア（simdsearch） | 3.2〜3.6 ms |

NumPy の 33 ms の内訳は、行列とベクトルの積が 5 ms、argpartition が 10 ms、残りは `norms - 2*g` の一時配列の確保と書き込み
Go の quickselect がヒープより遅いのは、100 万件の距離を 8MB の配列に書いてから分割するためで、K=20 のヒープはほとんどの点を根との比較 1 回で捨てる

### 10 万件、d=128、K=20、クエリ 1,000

正規乱数（ANN に最も不利）と、1,000 個の中心の混合ガウスを長さ 1 にしたもの（埋め込みに近い）
「B/件」の `a+b` は、符号 a バイトに加えて並べ直し用に元のベクトル b バイトを持つことを表す

混合ガウスの主な行

| 方式 | パラメータ | recall@20 | 1 クエリ | B/件 | 構築 |
| --- | --- | --- | --- | --- | --- |
| 全探索 | - | 1.000 | 4.44 ms | 516 | - |
| IVF-Flat | nlist=316 nprobe=4 | 0.907 | 112 µs | 520 | 0.96 s |
| IVF-Flat | nlist=316 nprobe=16 | 0.955 | 405 µs | 520 | 0.96 s |
| PQ（ADC のみ） | M=8 K=256 | 0.416 | 556 µs | 8 | 1.04 s |
| PQ + 再ランキング | M=8 候補 10×K | 0.984 | 673 µs | 8+516 | 1.04 s |
| PQ + 再ランキング | M=16 候補 4×K | 0.986 | 957 µs | 16+516 | 1.15 s |
| IVF-PQ（残差）+ 再ランキング | M=16 nprobe=16 候補 10×K | 0.955 | 486 µs | 20+516 | 2.58 s |
| LSH（256 ビット全走査）+ 再ランキング | 候補 100 | 0.942 | 471 µs | 32+516 | 0.09 s |
| LSH 転置（マルチプローブ） | b=8 表 4 バケット 5/表 | 0.559 | 992 µs | 16+516 | 0.02 s |
| HNSW | M=16 efC=200 efSearch=20 | 0.973 | 59 µs | 674 | 43 s |
| HNSW | M=16 efC=200 efSearch=40 | 0.999 | 90 µs | 674 | 43 s |

正規乱数では、同じ設定で IVF-Flat nprobe=16 が 0.284、HNSW efSearch=320 が 0.783、PQ M=8 が 0.047 まで落ちる
近傍に構造が無いので、どの方式も「近い点の集まり」を使えない

### 100 万件、d=128、K=20、クエリ 1,000

HNSW は 1 スレッドで挿入するので、構築は efC=100 でも 257〜539 秒かかった。NSW は省いた

### メモリ（ヒープの実測）

| 対象 | ヒープの増分 | 1 件あたり |
| --- | --- | --- |
| fp32 の元のベクトル、100 万件 x 128 次元 | 512.0 MB | 512 B |
| PQ の符号（M=8、K=256）、100 万件 | 8.0 MB | 8 B（1/64） |
| SimHash 256 ビット、100 万件 | 32.1 MB | 32 B（1/16） |
| HNSW のグラフ（M=16、ベクトル本体を除く）、10 万件 | 16.6 MB | 166 B |

教材は倍精度で 128 x 8 = 1,024 バイトが 8 バイト（1/128）になるとしている
fp32 では 512 バイトが 8 バイトで 1/64 になり、10 億件なら 512GB が 8GB になる。PQ の中心は全体で 128KB

### IVF で距離を計算する件数

教材の例（10 億件、k=65,536、nprobe=4 で 1 クラスタ平均 15,258 件、約 6 万件）を、100 万件、nlist=64、nprobe=4（平均 15,625 件、計算上 62,500 件）に縮めて数えた

| データ | クラスタの大きさ | 計算した件数の平均 | 最小〜最大 | recall@20 |
| --- | --- | --- | --- | --- |
| 正規乱数 | 1〜32,990 | 83,970 | 42,764〜119,913 | 0.255 |
| 混合ガウス | 4,753〜24,811 | 67,382 | 51,204〜89,159 | 0.698 |

平均の 4 倍より多くなるのは、大きいクラスタほど空間を広く覆い、クエリの近くに来やすいため
件数の見積もりは「N/k x nprobe」を下限と考え、クラスタの大きさの偏りで 1.1〜1.3 倍に増えると見ておく

### 二値化（256 次元 → 256 ビット、10 万件）

fp32 の 1,024 バイトが 32 バイト（1/32）になり、全件では 102.4MB が 3.2MB になる

| 方式 | 混合ガウス recall@20 | 正規乱数 recall@20 | 1 クエリ |
| --- | --- | --- | --- |
| fp32 の L2 全走査 | 1.000 | 1.000 | 9.4 ms |
| 各成分の符号 256 ビットのハミング全走査 | 0.452 | 0.038 | 0.41 ms |
| 符号で 100 件 → fp32 で並べ直し | 0.993 | 0.112 | 0.52 ms |
| 符号で 400 件 → fp32 で並べ直し | 1.000 | 0.251 | 0.59 ms |

100 万件 x 256 ビットのハミング全走査は、スカラの `bits.OnesCount64` が 4.9〜5.9 ms、archsimd の `OnesCount` 版が 6.9〜7.5 ms だった（simdsearch の `BenchmarkHamming256Scan`）
arm64 のスカラ版はもともと Neon の CNT 命令にコンパイルされるので、archsimd で書き直しても速くならない

### SimHash の一致率と層の分布

角度 θ の 2 本で 1 ビットが一致する割合は、65,536 枚の超平面で 10° 0.944（理論 0.944）、45° 0.752（0.750）、90° 0.504（0.500）、135° 0.253（0.250）
100 万点の最上層は 937,420 / 58,649 / 3,687 / 228 / 14 / 2 で、層ごとに 1/16 に減る（M=16 の期待値 937,500 / 58,594 / 3,662 / 229 / 14 / 0.9）

## 分かったこと

**SIMD の内積だけで NumPy の 2 倍速くなる**
スカラの Go は 1 本の全探索で NumPy とほぼ同じ時間だった
Neon で 8 本のアキュムレータを使う内積に替えると 17〜19 ms になり、1 コアで NumPy（OpenBLAS）の半分の時間になる

**バッチ化はレジスタの上で x を使い回して初めて効く**
1 ブロックを読むたびに全クエリと 1 本ずつ内積を取る書き方は、1 本ずつの全探索より遅かった
スカラの内積は帯域ではなく演算で律速しているので、DRAM から読む回数を減らしても速くならない
x の各成分を 1 回読んで 4 本のクエリと掛ける `dot4` にすると、積和 4 回あたりの読み出しが 8 回から 5 回に減り、1 goroutine で 1 本ずつの 44〜49 ms が 30 ms になった
全コアでは 1 本ずつ流すと 8.0〜10.5 ms、32 本まとめると 2.0〜5.8 ms

**PQ は単独では recall が低く、再ランキングとの組で使う**
M=8（8 バイト、fp32 の 1/64）の ADC だけでは混合ガウスでも recall@20 が 0.42 に留まる
近似距離で 4〜10 倍の候補を取って元のベクトルで並べ直すと 0.91〜0.98 に戻り、時間はほとんど増えない
ただし元のベクトルをどこかに持つ必要があるので、メモリを 1/64 にしたいだけなら並べ直しは使えない

**距離表を外すと PQ は 10 倍遅い**
10 万件、M=8、K=256 で、距離表ありが 0.55 ms、符号ごとに中心との距離を計算し直すと 5.9 ms

**IVF-PQ の残差はこの分布ではほとんど効かない**
混合ガウスの散らばりを中心の長さと同じにしたので、残差の幅は元のベクトルとあまり変わらない
M=16 nprobe=16 で残差 0.561、元のベクトル 0.534
クラスタごとに距離表を作り直すので、nprobe=64 では残差の版が元のベクトルの版より 4.7 倍遅い

**データを見て切るクラスタは、データを見ない超平面より同じ計算量で recall が高い**
IVF-Flat nprobe=1 は 738 件の距離計算で recall 0.844
LSH 転置（b=8、表 4、各表 1 バケット）は 1,692 件で 0.194
超平面は点の集まりと無関係に空間を切るので、近い点が別のバケットに落ちる

**グラフの探索は、件数が大きく塊がはっきりすると IVF に負ける**
10 万件の混合ガウスでは HNSW efSearch=40 が 90 µs で 0.999 と最も速かった
100 万件では HNSW efSearch=80 が 241 µs で 0.904 に留まり、IVF-Flat nprobe=1 の 100 µs で 0.983 に負けた
efC を 100 に下げたことと、塊の間をつなぐ辺が足りないことが考えられるが、efC=200 では確かめていない

**128 次元では HNSW の階層はほとんど効かない**
128 次元の混合ガウスでは、NSW（1 層）と HNSW の recall / 距離計算の数がほぼ同じだった
近傍グラフの直径がもともと数ホップしかないので、上の層で縮める距離が無い
4 次元の一様乱数では差が N とともに開いた

| N | HNSW | HNSW の層 0 だけ | NSW（1 層） | 正確な 16 近傍グラフ |
| --- | --- | --- | --- | --- |
| 1 万 | 5.6 | 8.1 | 9.2 | 10.5 |
| 10 万 | 7.8 | 12.0 | 13.5 | 18.7 |
| 100 万 | 8.5 | 19.2 | 24.7 | - |

値は貪欲探索（候補 1 つ）で移動した辺の数の平均
候補 1 つの貪欲探索は極小で止まり、recall@1 は 128 次元の混合ガウス 10 万件で 0.23 だった。ef=20 の優先度付きキューにすると recall@20 が 0.973 になる

**長い辺の無いグラフは塊の間を渡れない**
正確な 16 近傍だけを結んだグラフは、128 次元の混合ガウス 10 万件で recall が 0 だった
入口の点が属する塊から外に出る辺が無く、クエリの塊にたどり着けない
