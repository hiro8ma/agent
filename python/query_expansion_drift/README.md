# query_expansion_drift

LLM に書かせた文でクエリを広げる手法（Query2doc / HyDE）で、元のクエリをどの重みで残すと検索が良くなるかを測る小さな実験
広げた文に引きずられて元の意図から外れ、検索が悪くなること（クエリドリフト）がどれだけ起きるかも数える
公開の IR データセット BEIR SciFact で、BM25 と密ベクトルの両方を比べる
生成はローカルの Gemma 3 4B（4bit 量子化）で行い、有料の API は使わない

## 確かめること

- 生成文だけで検索する設定（元のクエリの重み0）と、元のクエリを重みで混ぜる設定のどちらが良いか
- 混ぜる重み（BM25 での元のクエリの繰り返し回数、密ベクトルの補間の α）をどこに置くと良いか
- 平均が良くなる設定でも、元のクエリだけより悪くなるクエリがどれだけあるか
- temperature 1.0で書き直すと、検索の結果がどれだけ振れるか

## データ

| 項目 | 値 |
|---|---|
| データセット | BEIR SciFact（科学の主張と、それを支持または否定する論文の要旨） |
| 文書数 | 5,183 |
| 評価に使うクエリ | テスト分割の300件を乱数の種0で並べ替えた先頭96件 |
| 正解 | クエリ1件あたり平均1.1件（BEIR の qrels、関連度はすべて1） |
| Query2doc の例 | 訓練分割の主張4件と、その正解文書の冒頭60語 |

- データは実行時に BEIR の配布元から取得して `cache/` に置き、SHA-256 を確かめる
- 取得したデータと生成文はコミットしない
- クエリを96件に減らしたのは、生成の時間を30分以内に収めるため
  - 200件を予定したが、同じ Mac でほかの MLX の生成と GPU を分け合って遅くなり、25分で止めた時点で生成が済んでいた96件を使った
  - 96件の元のクエリだけの nDCG@10 は BM25 で0.703、密ベクトルで0.714で、300件全体の0.663と0.645より高く、易しい側に寄っている
- 例の4件は、正解文書がテスト分割の正解に含まれない訓練の主張から選ぶ

## 生成

| 形式 | 指示の中身 | 最大トークン数 | 平均トークン数 |
|---|---|---:|---:|
| Query2doc | 例を4組見せ、主張に対応する論文の要旨の一節を書かせる | 128 | 103.2 |
| HyDE | 例なしで、主張を支持または否定する論文の一節を書かせる（HyDE 論文の SciFact 用の指示） | 128 | 126.0 |
| 性質の列挙 | 関連する要旨に含まれてほしい遺伝子、たんぱく質、薬、病気、細胞の種類、生物、結果の語と同義語を、カンマ区切りで並べさせる | 64 | 64.0 |

- 各クエリと各形式で、temperature 0で1本、temperature 1.0で3本書かせる
  - top-p などの絞り込みはしない
- HyDE と性質の列挙は、ほぼすべてが最大トークン数で切れている
- 性質の列挙は、検索で一致してほしい性質だけを書かせる書き換えに近い形にした
  - 最初の指示はカテゴリの名前（entities, populations など）を並べたもので、モデルがカテゴリの名前そのものを書いたので、具体的な語を求める指示に一度だけ書き直した
- 指示の全文は `prompts.py` にある

## 検索

文書は「タイトル + 本文」で索引し、5,183件を全探索する

| 検索 | 設定 | 中身 |
|---|---|---|
| BM25 | 元のクエリだけ | 基準 |
| BM25 | 生成文だけ | 元のクエリの重み0 |
| BM25 | 元のクエリ×n + 生成文 | 元のクエリを n 回繰り返して生成文と連結する（n=1, 3, 5、Query2doc 論文は n=5） |
| 密ベクトル | α=1（元のクエリだけ） | 基準 |
| 密ベクトル | α=0.8〜0（生成文だけ） | 正規化した e(q) と e(生成文) を α e(q) + (1-α) e(生成文) で混ぜる |
| 密ベクトル | 連結した文字列 | 「元のクエリ + 生成文」の文字列を埋め込む |
| 密ベクトル | 元のクエリと T=1の3本の平均 | e(q) と temperature 1.0の3本の埋め込みの平均（HyDE 論文の扱い） |

- BM25 は自前の実装で、k1=0.9、b=0.4（Anserini の既定）
  - クエリの語は出現回数だけ足し合わせるので、元のクエリを n 回繰り返すと元の語の重みが n 倍になる
  - 小文字にして英数字で区切り、Lucene の既定の英語の停止語を除く
  - 語幹の処理はしない
- 密ベクトルは all-MiniLM-L6-v2 で、文書とクエリの埋め込みを正規化して内積で順位を付ける
  - 入力は256トークンで切れる

## 指標

- nDCG@10 と Recall@100
- 悪化と改善は、クエリごとの nDCG@10 が同じ検索の基準（元のクエリだけ）より下がったか上がったかで数える
  - 平均の差の95%区間は、クエリごとの差の平均に ±1.96 × 標準誤差を付けたもの
- temperature 1.0の3本は、設定ごとに3本それぞれの nDCG@10 を出し、最良と最悪の差を振れ幅とする
  - 上位10件の重なりは、3本から2本を選ぶ3通りで上位10件の共通の件数を10で割り、クエリと組で平均したもの

## 実行

```bash
uv sync
uv run pytest
uv run python experiment.py --n-queries 96
```

- LLM と埋め込みのモデルは Hugging Face のキャッシュにあればそれを使い、無ければ初回に取得する
- 生成文は `cache/generations.jsonl` に貯め、2回目からは生成しない
- 取得したデータ、文書の埋め込み、結果の表（`cache/results.md`）も `cache/` に置く
- `--n-queries` を変えても並べ替えの順は同じなので、少なくすれば貯めた生成文をそのまま使える

  - 生成文の冒頭は3本のうち1本目で、ほかの2本は世界の罹患率の傾向を書いていた

## 結果の読み方

- BM25 では生成文だけはどの形式でも元のクエリより悪く、元のクエリを5回繰り返すと Query2doc で+0.032、性質の列挙で+0.041上がって95%区間が0をまたがなかった（HyDE は+0.010で0をまたいだ）
- 密ベクトルでは生成文だけが HyDE で-0.080、性質の列挙で-0.112下がり、元のクエリを残しても上げ幅は最大+0.023で、区間が0より上に収まったのは性質の列挙の α=0.8（下限+0.000）だけだった
- 3つの形式すべてで基準を下回らなかったのは元のクエリを重く残す設定（BM25 の5回、α=0.6と0.8）だけで、Recall@100 は BM25 で生成文を使う12の設定すべてが基準の0.880を上回った
- 平均が上がる設定でも悪化するクエリは残り、BM25 の元のクエリ×5でも96件のうち Query2doc で4件、HyDE と性質の列挙で9件が下がった
- temperature 1.0で書き直すと、上位10件の重なりは生成文だけで0.46〜0.62、BM25 の5回で0.76〜0.82、α=0.8で0.90〜0.92と元のクエリの重みとともに大きくなったが、nDCG@10 の振れ幅（最大0.064）が重みとともに小さくなったのは BM25 の Query2doc と HyDE だけだった
