# japanese_tokenization

日本語の文章が LLM のトークナイザで何トークンになるかを測る実験
日本語の文書を LLM に全文で入れるかを決めるときに、文字数からトークン数を見積もる係数を出す
あわせて、同じコーパスと同じ語彙数で学習した BPE とユニグラム言語モデルの分割を比べる
有料の API は呼ばず、CPU で数秒で終わる

## 確かめること

- 日本語は1文字あたり何トークンになるか、トークナイザと文書の種類でどれだけ変わるか
- 「滅」のような漢字が、1文字の途中で複数のトークンに割れるか
- 同じ語彙数の BPE とユニグラムで、トークン数と分割がどう違うか

## 測る文章

| 文書 | 中身 | 置き場所 |
|---|---|---|
| 憲法 第1〜80条 | 日本国憲法の第一条から第八十条 | `../../go/internal/enginecmp/kenpou.json`（e-Gov 法令 API から取得したもの） |
| 憲法 第81〜103条 | 日本国憲法の第八十一条から第百三条 | 同上 |
| 吾輩は猫である 冒頭 | 夏目漱石の小説の冒頭 | `texts/wagahai.txt`（青空文庫、`../../go/cmd/gpt/main.go` の動作確認用の文章と同じ） |
| 技術文書の例 | 架空の検索 API のキャッシュ設計メモ | `texts/tech_note.txt`（この実験のために書いた） |

- 法令は著作権法第13条により著作権の目的とならない
- 夏目漱石の作品は著作権の保護期間が切れている
- 憲法の条は改行でつなぐ
- 文字数は Python の `len`（Unicode のコードポイントの数）で数え、改行と全角空白も1文字に数える
- 短い文は、教材の例3つ（カレーライスはおいしい、こんにちは、仏滅にはカレーを食べない）に、カタカナが多い文、漢字が多い文、英数字が混ざる文、英語の文を足した

## トークナイザ

| 名前 | 方式 | 語彙数 | 取得元 |
|---|---|---:|---|
| o200k_base | バイト単位の BPE | 200,019 | tiktoken（GPT-4o などが使う） |
| cl100k_base | バイト単位の BPE | 100,277 | tiktoken（GPT-4 と GPT-3.5 が使う） |
| Qwen3 | バイト単位の BPE | 151,669 | Hugging Face の `Qwen/Qwen3-0.6B` |
| llm-jp-3 | ユニグラム言語モデル（語彙に無い文字はバイトに落とす） | 99,574 | Hugging Face の `llm-jp/llm-jp-3-1.8b` |
| 自作 BPE（バイト単位） | バイト単位の BPE | 1,000 | `../transformer_training/bpe.py` を憲法 第1〜80条で学習 |
| SentencePiece BPE | 文字単位の BPE（語彙に無い文字はバイトに落とす） | 1,000 | sentencepiece を憲法 第1〜80条で学習 |
| SentencePiece ユニグラム | ユニグラム言語モデル（語彙に無い文字はバイトに落とす） | 1,000 | sentencepiece を憲法 第1〜80条で学習 |

- 自作の3つは語彙数を1,000にそろえた
  - ユニグラムは学習コーパスの部分文字列から候補を集めて削るので、7,550文字のコーパスでは語彙数1,395が上限だった
  - 1,000のうち256はバイトで、1つは特殊トークン（自作 BPE は文書の区切り、SentencePiece は未知語）
  - SentencePiece は空白の印を語彙に1つ足したので、文字と部分語に使える枠が自作 BPE より1つ少ない
- 自作 BPE は bpe.py の GPT-2 の事前分割をそのまま使う
  - 漢字、かな、カタカナはどれも文字の分類に入るので、日本語は句読点、記号、数字、空白の位置でだけ区切られる
- SentencePiece は、正規化と空白の詰めを切り、文頭に空白の印を足さない設定で学習した
  - decode で元の文字列に戻すため
- Claude のトークナイザは公開されていないので測っていない
- Gemma 3 は技術報告で Gemini 2.0 と同じトークナイザとされているが、Hugging Face の公式のリポジトリは利用規約への同意（ログイン）が要るので外した

## 実行

```sh
cd python/japanese_tokenization
uv sync
uv run python experiment.py   # 結果を Markdown で標準出力に書く
uv run pytest
uv run ruff check . && uv run ruff format --check . && uv run mypy .
```

- 初回は tiktoken と Hugging Face のトークナイザを取得する
- Hugging Face のトークナイザを取得できなかったときは、そのトークナイザを外して続け、外したことを出力に書く
- 2回目以降はこの環境で約2秒で終わる

## 実行環境

- Python 3.13.11、macOS-26.7.1-arm64-arm-64bit-Mach-O
- tiktoken 0.14.0、tokenizers 0.23.3、sentencepiece 0.2.2、regex 2026.9.29
- どのトークナイザも、すべての文書と短い文で encode と decode の往復で元に戻った
- 2026-10-25に実行した

## 読み方

- 1文字あたりのトークン数は、トークン数を文字数で割った値で、小さいほど同じ文章が少ないトークンで入る
- 自作の3つは憲法 第1〜80条で学習したので、その列は学習データそのものを測っている
- 憲法 第81〜103条は同じ文体で学習に使っていない文章、残りの2つは文体も違う文章にあたる
- 公開トークナイザの語彙は自作の約100〜200倍あるので、自作の3つは公開トークナイザと比べるためではなく、BPE とユニグラムを同じ条件で比べるために置いている

## 日本語は1文字あたり何トークンと見積もればよいか

測った4つの文書の範囲では次のとおり

| トークナイザ | 1文字あたりのトークン数 | 最も多かった文書 | 最も少なかった文書 |
|---|---:|---|---|
| o200k_base | 0.69〜0.86 | 憲法 第1〜80条 | 技術文書の例 |
| cl100k_base | 0.91〜1.16 | 憲法 | 技術文書の例 |
| Qwen3 | 0.68〜0.71 | 憲法 第1〜80条 | 吾輩は猫である 冒頭、技術文書の例 |
| llm-jp-3 | 0.50〜0.56 | 憲法 | 技術文書の例 |

- 新しい多言語のトークナイザ（o200k_base、Qwen3）では、日本語は1文字あたり0.7〜0.9トークンと見積もれる（測った値は0.68〜0.86）
- o200k_base と cl100k_base では、漢字の多い硬い文章ほど多く、英単語の混ざる技術文書ほど少ない
  - 英単語は1トークンで数文字を覆う（英数字が混ざる文では、前の空白を含む `replicas` の9文字が1トークン）

- 1文字あたりで比べると、英語の文（28文字で7トークン、0.25）は日本語の約3分の1になる
  - ただし、同じ内容の「カレーライスはおいしい」は o200k_base で8トークンで、英語の文の7トークンとほとんど変わらない（1文だけの比較）
- Claude と Gemini には、この係数をそのまま当てはめない
  - 手元の文書を数件、使うモデルのトークン数を数える API で数えて確かめる（API キーが要るので、この実験では呼ばない）

## 分かったこと

- 「滅」は o200k_base と cl100k_base で2トークン（`<e6 bb>` と `<85>`）に割れ、Qwen3 と llm-jp-3 では1トークンだった
  - 「仏」は o200k_base、cl100k_base、Qwen3 の3つで2トークンに割れた
- 漢字が多い文（18文字）は、cl100k_base で30トークン、o200k_base で17、Qwen3 で18、llm-jp-3 で10だった
  - cl100k_base は「給」「検」のような常用漢字でも1文字を2〜3トークンに割り、文書全体でも11.1〜21.5%の文字が割れた
  - o200k_base は割れた文字が1.5〜3.7%だった
  - o200k_base は語彙が cl100k_base の約2倍あり、漢字の多くを1トークンとして持っている
- llm-jp-3 はどの文書でも割れた文字が0%だった
  - 測った文章の文字がすべて語彙に入っていて、バイトに落ちた文字が無かった
- 自作の3つは、学習に使った憲法 第1〜80条では1文字あたり0.62で、llm-jp-3 を除く公開トークナイザより少なかった
  - 学習に使っていない第81〜103条では0.75〜0.78、文体の違う2つの文書では1.30〜1.57と1を超えた
  - 憲法に出ないカタカナは、SentencePiece では1文字がバイトのトークン3つになる
  - 自作 BPE は、ひらがなとカタカナの一部が共有する先頭の2バイト（`<e3 82>`）を1トークンにしていて、そのカタカナは1文字が2トークンで済む
  - 技術文書のカタカナ121文字は、自作 BPE で316トークン、SentencePiece BPE で363トークンだった
  - カタカナ以外では自作 BPE のほうが7トークン多く、技術文書全体で自作 BPE が少なかったのはカタカナの分だった
- 自作の BPE とユニグラムは、トークン数がほとんど同じだった（学習に使った文書で4,692と4,691、第81〜103条で1,517と1,544）
- 一方で語彙と分割は違った
  - 文字とバイト以外の部分語743個のうち640個が共通で、103個ずつが違った
  - BPE だけにある部分語は「しなければならない」「することができる」のように、条をまたいで何度も出る言い回しだった
  - BPE は隣り合う2つの部分語の頻度で語彙を足すので、長い部分語は途中の部分語も頻出でないとできない
  - ユニグラムだけにある部分語は「国会休会中の期間を除いて」「両議院の協議会を開」のように、特定の条に出る長い句だった
  - ユニグラムは候補の部分文字列を多めに集めてから、削ってもコーパスの尤度があまり下がらない部分語から削る
  - 長い句は、削ると出るたびに複数の部分語に割ることになり尤度が大きく下がるので、数回しか出なくても残りやすい
  - その分、学習に使っていない第81〜103条ではユニグラムが「憲 / 法」「裁 / 判」と1文字ずつに割る箇所があり、BPE より27トークン多かった
- ユニグラムは1つの句に分割の候補を複数持ち、尤度の順に並べられる
  - BPE は学習したマージを順に当てはめるので、分割は1通りに決まる
  - 学習時に候補から分割を選び直す正則化（subword regularization）は、この性質を使う

## 制約

- 文書は4つで、最大でも7,550文字
- 社内文書の代わりに置いた技術文書は、自作の588文字の1つだけ
- 自作の3つは7,550文字で学習したので、学習した文体に強く寄る
  - 大量の文章で学習した公開トークナイザとは規模が違い、トークン数の大小は比べられない
- 文字数はコードポイントで数えたので、Markdown の記号や改行も文字に入る
